**Research Note**

`RDEP` in these repos is not residual-based dynamic expert pruning. In `nmoe`/`modal-nmoe`, it is a route-row dispatch/expert-parallel transport system: explicit `(token, slot)` rows are shipped to expert owners, computed there, then returned. I did not find any pruning or token-dropping policy beyond standard top-`k` routing.

`nmoe` is the newer, richer branch. `modal-nmoe` has the same core RDEP/blockscaled design, but `nmoe` adds newer diagnostics and training refinements; I did not find a distinct MoE transport/routing technique in `modal-nmoe` that is absent from `nmoe`.

**Routing And Utilization**

- `DeepSeek-style top-k router with aux-free bias balancing` uses `sigmoid(gate(x))`, selects experts by `scores + bias`, renormalizes selected scores, then optionally scales routed weights post-normalization ([model.py](/tmp/moe/nmoe/nmoe/model.py:66), [opt.py](/tmp/moe/nmoe/nmoe/opt.py:656)). This is a direct fit for your `standard_moe`/`global_moe`/`moe_everything` models. Stability and utilization.
- `Optional Switch-style aux loss` is still implemented, but most MoE configs run `aux_loss_alpha=0` and rely on bias updates instead ([model.py](/tmp/moe/nmoe/nmoe/model.py:182), [train.py](/tmp/moe/nmoe/nmoe/train.py:463), [small_moe.toml](/tmp/moe/nmoe/configs/speedrun/small_moe.toml:78)). Applicable as an escape hatch for smaller-batch or unstable runs. Stability.
- `Shared experts` add an always-on MLP branch beside routed experts ([model.py](/tmp/moe/nmoe/nmoe/model.py:128), [config.py](/tmp/moe/nmoe/nmoe/config.py:43)). This maps cleanly onto any MoE variant in your stack and is a practical way to keep a dense gradient path alive. Stability, sometimes quality more than raw throughput.
- `Global router telemetry` aggregates loads and importance across ranks, not just locally, then logs CV, entropy, active experts, max load, and dead experts ([model.py](/tmp/moe/nmoe/nmoe/model.py:333), [metrics.py](/tmp/moe/nmoe/nmoe/metrics.py:1114), [metrics.py](/tmp/moe/nmoe/nmoe/metrics.py:1213)). This is directly worth copying into your codebase. Stability and utilization.
- `Router collapse detection` fails fast when routing degenerates toward only `K` active experts using a CV-based signature ([train.py](/tmp/moe/nmoe/nmoe/train.py:589)). Very applicable to your training harness. Stability.

**Dispatch And IPC**

- `RDEP pooled route rows` encodes each routed selection as a `row_id=((src_rank*T)+tok)*K+slot`, batches rows from all replicas onto the owner GPU, and reconstructs outputs by `row_id` rather than packed-prefix assumptions ([0009-rdep.md](/tmp/moe/nmoe/content/0009-rdep.md:39), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:337), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:3309)). This is the main technique for `global_moe`/`moe_everything`; it is not useful for dense or purely local `standard_moe`. Throughput.
- `No-drop capacity provisioning` avoids capacity factors and token dropping: capacity is sized to worst-case `T*K*world`, and the Python path hard-errors if buffers are too small ([model.py](/tmp/moe/nmoe/nmoe/model.py:277), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:323)). This is a good trade if you prefer deterministic training semantics over slightly lower memory. Stability and correctness.
- `CUDA IPC intra-node` does a one-time `all_gather` of `cudaIpcMemHandle_t`, opens peer buffers once, then copies pointer arrays to device memory so kernels can dereference them directly ([rdep.py](/tmp/moe/nmoe/nmoe/rdep.py:49), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:444), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:512)). This is directly applicable if your `global_moe` path owns full experts per rank and keeps expert weights outside FSDP sharding. Throughput.
- `Hybrid IPC + NVSHMEM` is the multi-node extension: intra-node traffic still uses separate `cudaMalloc` IPC buffers, inter-node traffic uses NVSHMEM symmetric buffers because NVSHMEM memory cannot be reopened via CUDA IPC ([rdep_nvshmem.cuh](/tmp/moe/nmoe/nmoe/csrc/rdep_nvshmem.cuh:75), [rdep_nvshmem.cu](/tmp/moe/nmoe/nmoe/csrc/rdep_nvshmem.cu:533), [rdep_nvshmem.cu](/tmp/moe/nmoe/nmoe/csrc/rdep_nvshmem.cu:1442)). Relevant only if your `global_moe` expands across nodes. Throughput.
- `Tok-slot staging for return, dGate, and dX` replaces all-to-all with fixed per-`(token,slot)` write targets plus local reductions ([rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:4049), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:5367), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:5654)). This fits your DeepSeek-style router extremely well because routing already produces stable top-`k` token slots. Throughput.

**Expert Compute And Throughput**

- `Sort by local expert ID, then pad once` is the core batching strategy: dispatch extracts local expert ids, radix-sorts rows, computes per-expert offsets, and builds padded contiguous batches for grouped GEMM ([rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:3228), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:361)). This is directly reusable with Triton grouped GEMM. Throughput.
- `Deterministic upper-bound padding` avoids an extra exact-`M_pad` host sync by overallocating to a safe bound and extending the last expert’s segment ([moe.py](/tmp/moe/nmoe/nmoe/moe.py:361), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:3245)). This is a good micro-optimization for your current grouped-GEMM path. Throughput.
- `GPU-built grouped GEMM metadata` avoids Python loops and CPU sync when launching grouped blockscaled GEMMs, and reuses metadata workspaces across calls ([grouped.py](/tmp/moe/nmoe/nmoe/blockscaled/grouped.py:2218), [grouped.py](/tmp/moe/nmoe/nmoe/blockscaled/grouped.py:2485)). This is highly applicable to your Triton grouped GEMM stack. Throughput.
- `Fused expert AdamW + cache emission` updates BF16 expert masters and emits FP8/NVFP4 weight caches in the same kernel, removing a separate cache-refresh phase ([opt.py](/tmp/moe/nmoe/nmoe/opt.py:267), [adamw.cu](/tmp/moe/nmoe/nmoe/csrc/adamw.cu:3), [bindings.cpp](/tmp/moe/nmoe/nmoe/csrc/bindings.cpp:908)). Strong fit if your expert path already uses quantized forward caches. Throughput and stability.
- `SonicMoE-style dGate identity` computes `dGate = <A, dA>` from post-activation and ungated gradient, so backward does not need to recompute `Ye` just to form gate gradients ([moe.py](/tmp/moe/nmoe/nmoe/moe.py:749), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:845), [rdep.cu](/tmp/moe/nmoe/nmoe/csrc/rdep.cu:5533)). This is directly applicable to SwiGLU experts in your stack. Throughput.

**Stability And Numerical Choices**

- `BF16 masters, FP32 router/output accumulations` are used throughout: router logits are cast to FP32, returned token outputs accumulate in FP32, `dX`/`dGates` accumulate in FP32, and normalization/division uses clamps ([model.py](/tmp/moe/nmoe/nmoe/model.py:79), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:344), [moe.py](/tmp/moe/nmoe/nmoe/moe.py:527)). This should carry over unchanged. Stability.
- `Higher expert beta2 and expert-specific optimizer handling` reflect the expectation of noisier sparse/quantized expert gradients ([config.py](/tmp/moe/nmoe/nmoe/config.py:105), [opt.py](/tmp/moe/nmoe/nmoe/opt.py:286)). Directly applicable if your experts train in FP8/NVFP4. Stability.
- `NVFP4 resonance dither` intentionally perturbs otherwise-stuck cached FP4 codes to reduce quantization stick-slip behavior, and `nmoe` logs nibble-flip canaries to monitor it ([adamw.cu](/tmp/moe/nmoe/nmoe/csrc/adamw.cu:41), [metrics.py](/tmp/moe/nmoe/nmoe/metrics.py:76), [metrics.py](/tmp/moe/nmoe/nmoe/metrics.py:1476)). Applicable only if you keep quantized expert caches. Mostly stability.
- `Expert LR caution` is explicit in the research notes: for BF16 + AdamW, the old `15x` expert-LR rule overshoots, and `1x` is the right baseline; `modal-nmoe` configs still show the older heuristic ([0008-expert-learning-rate.md](/tmp/moe/nmoe/content/0008-expert-learning-rate.md:14), [moonlet.toml](/tmp/moe/nmoe/configs/moonlet.toml:37), [modal moonlet.toml](/tmp/moe/modal-nmoe/configs/moonlet.toml:37)). If your code still boosts expert LR aggressively, this is worth revisiting. Stability.
- `Dense params replicated, expert params separately sharded` is the architectural split: dense path uses ZeRO-2/DDP-style handling, expert path assumes owner-local full expert weights and custom transport ([zero2.py](/tmp/moe/nmoe/nmoe/zero2.py:130), [opt.py](/tmp/moe/nmoe/nmoe/opt.py:613), [0000-why-training-moes-is-hard.md](/tmp/moe/nmoe/content/0000-why-training-moes-is-hard.md:64)). For your DDP/FSDP stack, the closest fit is: keep dense under DDP/FSDP, keep globally-routed experts out of FSDP, and let the expert-parallel path own routing/dispatch.
