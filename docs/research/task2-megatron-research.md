**1. Grouped GEMM for expert compute**

- Megatron’s training path uses Transformer Engine grouped linear layers, not Triton, when `--moe-grouped-gemm` is enabled. `TEGroupedMLP` runs one FC1 and one FC2 grouped GEMM across all local experts, and falls back to `SequentialMLP` otherwise. Refs: [experts.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/experts.py:156), [transformer_engine_spec_provider.py](/tmp/moe/Megatron-LM/megatron/core/extensions/transformer_engine_spec_provider.py:75), [transformer_engine.py](/tmp/moe/Megatron-LM/megatron/core/extensions/transformer_engine.py:1674)
- What it does: batches many small per-expert GEMMs into one grouped launch, which mainly helps when `num_local_experts > 1` and each expert sees few tokens. Megatron’s own config text explicitly frames it as a utilization fix for “multiple local (potentially small) gemms.” Refs: [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:728), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:445)
- How it works: the token dispatcher permutes tokens so each local expert gets a contiguous slice; `tokens_per_expert` is passed into grouped FC1/FC2; TE handles the grouped GEMM while Megatron handles TP/EP comm explicitly outside TE (`explicit_expert_comm`). Refs: [token_dispatcher.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/token_dispatcher.py:597), [moe_layer.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_layer.py:495), [transformer_engine.py](/tmp/moe/Megatron-LM/megatron/core/extensions/transformer_engine.py:1729)
- Performance characteristics: this is a pure throughput technique. It reduces launch overhead and improves Tensor Core occupancy; benefit is small when you already have one expert per rank. Megatron also folds probability weighting into the activation path instead of the final unpermute path to save memory traffic. Refs: [experts.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/experts.py:270), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:30)
- Applicability to your stack: highly applicable conceptually. Your Triton grouped GEMM is the closest analogue to Megatron’s TE grouped GEMM. The transferable parts are the data layout contract (`tokens_per_expert`, contiguous per-expert slices, optional alignment padding), not the exact kernel backend. One nuance: Megatron’s Triton-style grouped MM path is inference-oriented (`mcore_fused_moe`), not the main training path. Refs: [experts.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/experts.py:640)
- Kernel/backend nuance: the legacy YAML path still asserts bf16 for grouped GEMM, but core config also has FP8 grouped GEMM checks with newer TE. So backend support depends on the config path and TE version. Refs: [yaml_arguments.py](/tmp/moe/Megatron-LM/megatron/training/yaml_arguments.py:267), [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:1853)

**2. Dispatcher selection and routing/load balancing**

- Megatron exposes three dispatcher families: `allgather`, `alltoall`, and `flex`. `allgather` gathers tokens over TP×EP then filters locally; `alltoall` does EP all-to-all plus TP gather/reduce-scatter; `flex` uses a unified TP×EP communication group and backend-specific fused dispatchers. Refs: [moe_layer.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_layer.py:275), [token_dispatcher.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/token_dispatcher.py:211), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:307)
- `flex + DeepEP`: fused permute + dispatch/combine, removes redundant tokens in cross-node communication, and expects fp32 routing probs. Good fit for DeepSeek-V3-style fine-grained routing. Refs: [token_dispatcher.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/token_dispatcher.py:1121), [fused_a2a.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/fused_a2a.py:69), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:310)
- `flex + HybridEP`: same abstraction, but uses NVIDIA’s HybridEP fused permute/A2A path and can avoid a sync when `num_permuted_tokens` is known. Also wants fp32 probs. Refs: [token_dispatcher.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/token_dispatcher.py:972), [fused_a2a.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/fused_a2a.py:332), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:311)
- Routing itself is `TopKRouter`, with support for post-softmax top-k, pre-softmax top-k, `softmax`/`sigmoid`/`sqrtsoftplus`, and DeepSeek-style grouped top-k. Group-limited routing first picks expert groups, then experts within those groups. Refs: [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:137), [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:675), [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:582)
- Load balancing options are richer than a standard aux loss: `aux_loss`, `seq_aux_loss`, `global_aux_loss`, `sinkhorn`, and aux-loss-free expert bias. `seq_aux_loss` is the DeepSeek-style per-sequence balancing loss; expert bias is updated after grad finalization using TP×CP×DP token counts. Refs: [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:285), [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:325), [finalize_model_grads.py](/tmp/moe/Megatron-LM/megatron/core/distributed/finalize_model_grads.py:293), [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:1162)
- Applicability to your stack: very high. Your “DeepSeek-style routing” matches Megatron’s most relevant path: pre-softmax + sigmoid, group-limited top-k, `seq_aux_loss`, optional expert bias, fp32 router. Megatron’s own DeepSeek test configs use exactly that bundle. Refs: [model_config.yaml](/tmp/moe/Megatron-LM/tests/functional_tests/test_cases/mixtral/deepseekv3_proxy_flex_tp1pp4emp16etp1cp1_release/model_config.yaml:99)
- Impact: mostly throughput via better balance and lower dispatcher overhead; secondarily stability because fp32 routing, smoother balancing losses, and expert-bias updates reduce pathological load skew.

**3. Communication overlap in expert parallel training**

- Megatron’s main EP overlap feature is batch-level A2A overlap: it merges forward and backward work from adjacent microbatches in a combined 1F1B schedule so EP all-to-all is hidden behind independent compute. Refs: [combined_1f1b.py](/tmp/moe/Megatron-LM/megatron/core/pipeline_parallel/combined_1f1b.py:139), [model_parallel_config.py](/tmp/moe/Megatron-LM/megatron/core/model_parallel_config.py:256), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:434)
- Constraints are strict: EP>1, `alltoall` or `flex`, bf16/fp16, no full MoE recompute, and VPP is required when PP>1. Megatron also warns that TP/CP can conflict with the `CUDA_DEVICE_MAX_CONNECTIONS` setting needed for best EP overlap. Refs: [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:2098), [arguments.py](/tmp/moe/Megatron-LM/megatron/training/arguments.py:1289)
- `delay_wgrad_compute` is the key companion technique: TE grouped GEMM splits dgrad and wgrad so expert weight-gradient work can be delayed and overlap better with communication. Refs: [transformer_engine.py](/tmp/moe/Megatron-LM/megatron/core/extensions/transformer_engine.py:1710), [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:2157)
- There is a second, more local overlap path for DDP/FSDP: `overlap_dispatch_backward_with_experts_wgrad`. Megatron records an event when expert dgrad finishes, launches expert wgrad on a separate CUDA stream, then triggers post-wgrad hooks such as FSDP reduce-scatter only after that stream finishes. Refs: [moe_layer.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_layer.py:670), [model_parallel_config.py](/tmp/moe/Megatron-LM/megatron/core/model_parallel_config.py:264), [megatron_fsdp.py](/tmp/moe/Megatron-LM/megatron/core/distributed/fsdp/src/megatron_fsdp/megatron_fsdp.py:1012)
- Shared experts have their own overlap path: shared-expert FC1/FC2 are scheduled around the token A2A on a side stream. Refs: [token_dispatcher.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/token_dispatcher.py:669), [shared_experts.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/shared_experts.py:147)
- Applicability to your stack: if you only use DDP/FSDP and not pipeline parallelism, the FSDP-style delayed expert wgrad path is the most directly portable. If you do have PP, the combined 1F1B overlap idea is also portable, but it is much more invasive than the delayed-wgrad stream pattern.
- Impact: throughput only.

**4. Training stability and numerical tricks**

- Router precision is a first-class stability knob. Megatron lets routing run in fp32/fp64 via a custom gating linear that preserves lower-precision inputs/weights but computes logits in higher precision; it warns when expert count is large and router dtype is left unset. Refs: [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:701), [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:1321), [transformer_config.py](/tmp/moe/Megatron-LM/megatron/core/transformer/transformer_config.py:2203)
- z-loss is implemented exactly as a router-logit regularizer for stability; input jitter is also supported. Refs: [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:497), [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:552)
- Aux-loss gradients are scaled with `MoEAuxLossAutoScaler` so they match the main-loss scaling under microbatching and per-token-loss normalization. This is one of the more useful MoE-specific stability details in Megatron. Refs: [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:249), [schedules.py](/tmp/moe/Megatron-LM/megatron/core/pipeline_parallel/schedules.py:282), [initialize.py](/tmp/moe/Megatron-LM/megatron/training/initialize.py:108)
- Optional token dropping/capacity limits exist, with either `probs` or `position` drop policy, but Megatron’s modern DeepSeek-style configs are dropless. Refs: [router.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/router.py:628), [moe_utils.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_utils.py:903)
- Gradient clipping is not MoE-specific. Megatron uses standard global clip-grad; the MoE-specific nuance is that norms/logging need expert-aware reductions across expert groups so expert params are not miscounted or missed. Refs: [optimizer.py](/tmp/moe/Megatron-LM/megatron/core/optimizer/optimizer.py:220), [training/utils.py](/tmp/moe/Megatron-LM/megatron/training/utils.py:155)
- Applicability to your stack: router fp32, z-loss, seq aux loss, and aux-loss scaling are all directly portable. If your router already runs in fp32 and you normalize per token, the most reusable Megatron idea is the explicit aux-loss scaling hook.

**5. Expert parallelism and expert placement**

- Experts are sharded contiguously across EP ranks: `num_local_experts = num_experts // ep_size`, and each rank owns a contiguous expert-id block. Refs: [moe_layer.py](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/moe_layer.py:165)
- Megatron builds separate groups for expert model parallel, expert tensor parallel, TP×EP, TP×EP×PP, and expert data parallel. That separation is what lets it treat expert params differently in communication, checkpointing, and norm reduction. Refs: [parallel_state.py](/tmp/moe/Megatron-LM/megatron/core/parallel_state.py:1169)
- In grouped expert layers, TE is intentionally made “agnostic” to TP comm for experts; the token dispatcher owns TP/EP comm, while grouped GEMM only sees local partitioned shapes. Refs: [transformer_engine.py](/tmp/moe/Megatron-LM/megatron/core/extensions/transformer_engine.py:1729)
- Megatron’s own guidance is to prefer EP over TP for MoE layers, keep EP×TP inside the NVLink domain, and often set expert TP to 1 for fine-grained MoE. Refs: [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:182), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:207), [README.md](/tmp/moe/Megatron-LM/megatron/core/transformer/moe/README.md:518)
- Applicability to your stack: fully applicable if you already use `torch.distributed` DDP/FSDP. The main practical takeaway is to keep expert ownership explicit, separate expert collectives from dense-model collectives, and avoid extra expert TP unless local expert GEMMs are still too large.

**Bottom line for your codebase**

The highest-value Megatron ideas for a DeepSeek-style, Triton-grouped-GEMM, `torch.distributed` DDP/FSDP stack are:

- Keep DeepSeek-style routing in fp32, with group-limited top-k and `seq_aux_loss`; add expert-bias balancing if aux loss becomes a bottleneck.
- Preserve a strict dispatcher/compute contract: contiguous per-expert token blocks plus `tokens_per_expert`.
- Borrow Megatron’s overlap pattern for FSDP first: delayed expert wgrad on a side stream, with post-wgrad reduction hooks.
- Treat expert params as a separate communication/statistics domain from dense params.
